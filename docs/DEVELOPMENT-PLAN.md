## 阶段 1：核心验证与缺陷梳理

确认启动、退出、配置保存与恢复、文件打开和程序启停可用，建立统一缺陷清单。影响数据或核心操作的问题先修复；完整视觉、DPI 和桌面验收在 UI 落地后执行，避免在即将替换的界面上重复验收。原有欠项全部保留。

## 阶段 2：UI/UX 设计

目标是形成用户认可的整体界面，不只调整颜色。先了解日常使用顺序、当前不满意之处和视觉偏好，再确定方案。

| 步骤 | 工作内容 | 可评审的结果 |
| --- | --- | --- |
| 结构梳理 | 明确工具列表、运行状态、单项操作、批量操作与设置入口的层级 | 页面结构和关键操作流程 |
| 主视觉探索 | 以控制面板为样板，提供 2–3 个有实质区别的方向，比较布局、信息密度和视觉气质 | 同一内容下的可比较设计稿；现有 A/B 作为参考，不预设沿用 |
| 关键页面设计 | 在确认方向上完善控制面板、设置中心、添加／编辑程序、文件打开面板与文件夹选择窗口 | 关键页面完整设计稿 |
| 组件与状态 | 统一字体层级、间距、颜色、图标、按钮、开关、列表和表单；补齐运行中、忙碌、失败、空列表与弹窗 | 可复用组件规范及状态稿 |
| 交互与适配 | 明确悬停、焦点、禁用、反馈、动效、最小窗口、浅深色及高对比度处理 | 关键交互演示或状态流程，以及适配要求 |
| 设计评审 | 用户查看真实页面效果并提出修改，更新设计稿并记录确认版本 | 确认的设计基线和剩余问题 |

后续备份与场景功能在此阶段只预留合理入口和扩展空间，不提前实现。视觉方向尚未确认时，不铺开所有窗口的高保真实现。

完成条件：用户明确认可主视觉与关键页面；常用操作层级清楚；组件和异常状态有规范；设计适应工具数量增加与窗口缩小。

## 阶段 3：UI 实现与打磨

先将控制面板设计实现为可运行样板，核对真实字体、图标、间距、状态和动效；确认实现符合设计后，再逐个替换其他窗口。规范落实到共享资源和组件，保留既有功能行为并完成回归。

每个窗口用设计稿和运行截图对照验收，检查实际 DPI、键盘操作、主题与高对比度适配，最后统一窗口之间的细节。设计更新先同步规范，避免只修一个页面。

## 阶段 5：配置备份与迁移

建议 1 天确定格式与导入规则、2 天实现、1 天异常验证、1 天验收交付。按已确认的 UI 规范设计新增页面后再实现。

- 首版导出工具列表、启动参数、用户设置及外观；说明可能包含本机路径和参数。文件夹访问历史不打包。
- 导入先预览新增、冲突和失效路径；替换或合并规则必须明确，不静默覆盖。
- 验证旧格式、损坏文件、重复工具、不同电脑路径和写入失败；失败保留原配置。

## 阶段 6：使用场景预设

建议 1 天明确交互与生命周期、2 天实现、1 天回归、1 天验收交付。新增界面沿用组件规范，并单独做设计检查。

- 首版支持场景名称、工具组合、启动顺序，以及新增、编辑、删除和一键启动。
- 例如“办公”启动 Everything 与 Ditto；“录音”启动无线麦及用户添加的录音软件。只引用已配置工具。
- 保留其他运行工具，已运行项跳过；失败显示到具体工具，不阻断其余启动。
- 工具删除或编辑后提示修复引用；保存重开及批量操作相互兼容。
- 首版不加入定时运行、自动关闭无关软件或复杂条件。

## 阶段 7：外部程序管理增强

先用可控测试程序验证，再按需测试实际软件。高级配置先设计再实现。

- 分别配置启动程序与实际监控程序，适配启动器启动后退出的情况；默认兼容旧配置。
- 继续限制完整路径、当前用户和会话，不扩大停止范围。
- 验证多实例、启动器提前退出、目标未出现、权限失败与旧配置恢复。

## 阶段 8：多显示器支持

建议 2 天验证识别和坐标模型、4 天实现、4 天布局与桌面验收。

- 先解决显示器选择及左／右／上接收条，再评估复杂跨屏行为；配置界面遵循 UI 规范。
- 必测负坐标、混合 DPI、主屏切换、插拔、工作区变化及面板避让。
- 缺少多屏设备时停留在验证阶段，不用离屏渲染替代桌面结论。
- 实现前更新主屏限制相关需求和领域文档，必要时新增 ADR。

## 里程碑与分工

| 里程碑 | 决策依据 |
| --- | --- |
| M1 核心基线可用 | 核心流程能操作，缺陷清单明确 |
| M2 设计基线确认 | 用户认可关键页面、视觉与交互；再进入全面 UI 实现 |
| M3 UI 落地通过 | 可运行页面与确认稿一致，功能回归及适配通过 |
| M4 稳定版候选验收 | 实际桌面、目标电脑与干净环境结果支持发布 |
| M5–M8 新功能逐项验收 | 分别依据备份恢复、场景执行、状态识别及多屏实测证据 |

开发代理负责设计方案、实现、可执行的本机验证与文档；用户确认视觉方向、页面效果和日常使用体验，并在开发环境无法覆盖时提供目标电脑、多屏和真实 UAC 场景的结果。缺少结果时标记未执行，不默认通过。

## 如何维护

1. 开始一个阶段前核对依赖、投入与窗口，将任务登记到 [TODO.md](dev-status/TODO.md) 和当日日志。
2. 每次开发后更新状态、证据和下一步；延期记录原因、剩余工作及新窗口。
3. 新功能实施前明确需求、设计新增界面，按需更新规范与 ADR；UI 检查贯穿后续开发，发布前再做整体打磨。
4. 新想法放入候选池，不直接插入正在执行的阶段。

候选池：文件临时收纳篮、更多原生工具，待实际使用反馈再评估。
